A small shop wants to let customers place orders online. The requirements are fairly simple. Customers should be able to browse products, choose a quantity, and submit an order. The shop's staff need to see those orders and prepare them. A development team builds the first version. There's a website for customers, an application running on a server, and a database running on another server. The application handles requests from the website. The database stores the products and orders. When a customer submits an order, the application checks the details, saves the order in the database, and sends back a confirmation. The team tests it. Customers can browse products. Orders are saved correctly. Staff can see them. They release the application, and the shop starts taking orders. For the first few weeks, everything works well. Then the shop runs a promotion. More customers visit at the same time. Product pages take longer to load, and some customers get errors when they try to place an order. The application still has the same features. But under this heavier traffic, it can no longer respond quickly enough. The team needs to find out why. They check the application and database. In this example, the database is keeping up but the application servers CPU is staying close to full usage. A test with similar traffic reproduces the slowdown. That gives the team somewhere to focus. They could give the application server more processing capacity. Or they could run copies of the application on additional servers and share the request between them. They decide to try a second application server. Now there are two copies of the application, both using the same database, but customers still need one address to visit. Something has to receive incoming requests and distribute them between the application servers. The team adds a load balancer to do that. They also check that either application server can handle an incoming request. If information needed for a customer's next request estern exists only on the first server, sending that request to the second one could cause a problem. After making the necessary changes, they repeat the traffic test. With this workload response times improve and fewer requests fail. The team has changed how the application handles demand. That change also has a cost. There's another application server to pay for. A load balancer to configure. And more infrastructure to monitor. [first 150 s, local whisper]
